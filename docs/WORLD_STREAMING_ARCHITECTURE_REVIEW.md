## Executive Summary

## Pipeline Map

1. Server configuration is read in `server/pkg/network/server.go`: view distance defaults to `10`, is clamped to `16`; batch size defaults to `64`; bootstrap radius defaults to `0`; chunk encoding defaults to RLE with `RUMPELMC_SERVER_CHUNK_ENCODING=raw` as rollback.
2. On connection, the server waits up to `250ms` for the first client position packet. If it arrives, `handleInitialClientPacket` streams around that initial chunk using the bootstrap radius; otherwise it falls back to `(0,0)`.
3. Normal position packets map player position to chunk coordinates and call `sendChunksAround`, which delegates to `world.ChunksAround` with full view distance and the per-update limit.
4. `world.ChunksAround` builds unsent coordinates inside the circular radius, sorts nearest-first by squared distance, truncates to the batch limit, then gets or creates chunk snapshots while holding the world mutex.
5. Chunk generation is currently versioned through explicit `GeneratorConfig`; default `flat_v1` still calls `GenerateFlat`, while opt-in `height_v1`, `biome_height_v1`, `cave_height_v1`, and `biome_cave_height_v1` keep the same chunk dimensions and serialized little-endian `u16` block array of `32 * 32 * 512 * 2` bytes.
6. Server RLE encodes serialized chunks with block-id plus uvarint run lengths, then sends protobuf `ChunkData` through TCP framing with a 4-byte little-endian length prefix.
7. The Rust client sends the initial position before starting the reader thread, then the reader thread receives framed protobuf packets, records read/decode timing, and forwards them through an unbounded standard channel to the Godot main thread.
8. Each Godot process tick drains all currently available packet records, records queue lag, and calls `update_chunk` for `ChunkData`.
9. `update_chunk` validates raw/RLE payloads, decodes to full raw chunk bytes, records startup packet/decode/insert/load milestones for the initial chunk, stores bytes in `chunk_blocks`, computes dirty updates, and queues affected subchunks.
10. The startup chunk has a special readiness path: it immediately dispatches the initial spawn subchunks, records collision readiness, and spawns the player only after collision exists.
11. Per frame, collision refresh is processed before mesh queue work. If collision rebuilt this frame, mesh queue processing is skipped for that frame.
12. `render_subchunk_mesh` builds padded subchunk blocks with neighbor borders, builds packed faces when needed, uploads GPU terrain faces when enabled, chooses GPU/CPU proxy/ArrayMesh behavior, applies collision, and records detailed mesh/collision/GPU upload timing.
13. Chunk unload is client-side and distance/grace based. Unloading removes chunk bytes, subchunk meshes, queued work, and then rerenders loaded neighbors.

## Invariants

- Wire compatibility: `Packet.chunk = 1`, `Packet.position = 2`, and `Packet.block_action = 3` must not be repurposed. New packet shapes need new field numbers and matching client/server tests.
- Raw chunk rollback must stay available through `RUMPELMC_SERVER_CHUNK_ENCODING=raw`.
- RLE decodes to exactly the same serialized raw bytes before normal chunk insert, dirty update, meshing, collision, and GPU upload behavior.
- Chunk dimensions and block serialization stay `32 x 32 x 512`, little-endian `u16`, index order `x + y * width * depth + z * width`.
- World generation and chunk serialization must remain deterministic.
- Startup readiness order must remain monotonic: packet -> inserted -> loaded -> mesh queued -> mesh dispatched -> first mesh -> collision -> player spawn.
- Player spawn must remain gated on startup chunk collision readiness.
- Draw distance, lighting, shadows, texture quality, and visible quality must not be reduced to improve performance.
- GPU repack remains default-off and is not justified by the current world-load measurement.
- PostgreSQL/RocksDB remain the only approved persistence database paths.

## Bottlenecks And Risks

1. Server world mutex scope is broad for future terrain. `world.ChunksAround` holds the world lock while selecting, loading/generating, serializing, snapshotting, and marking chunks sent. This is acceptable for current flat generation but will become pressure when worldgen, storage load, or multi-client scheduling gets heavier.
2. Server scheduling is nearest-first but not direction-aware. It does not prioritize chunks by movement vector, camera direction, predicted next chunk, collision needs, or visible gaps.
3. Server backpressure is static. Batch size is configurable, but the server does not consume client-side queue lag, decode time, terrain queue time, or resident pressure before deciding how many chunks to send.
4. Packet queue is unbounded. The reader thread can continue sending records while the main thread drains all available packets each frame. There is latency tracking, but no explicit queue limit, starvation alert, or drop/backpressure policy.
5. Startup wall clock is not dominated by chunk decode. The fresh startup chunk decode work is below `1ms`, while queue lag and scheduling/frame timing are much larger. Optimizing RLE decode alone will not move first playable latency much.
6. Current high-pressure evidence is still too small. GPU and draw-command headroom are large at the current resident set, so a larger world-load benchmark is required before GPU memory/repack work becomes the main performance target.
7. Client unload can create rerender churn. `unload_far_chunks` removes full chunks and rerenders loaded neighbors after grace/distance expiry. Fast turn, snap-back, or teleport-like movement should measure churn explicitly before changing policy.
8. Collision readiness is protected but can compete with render readiness. Collision refresh is processed before mesh work, and mesh work pauses after a collision rebuild. This protects gameplay correctness but needs starvation metrics under high movement pressure.
9. RLE assumptions depend on terrain entropy. The flat generated world compresses extremely well; caves, biomes, structures, liquids, and block edits may reduce compression ratio and raise CPU cost.
10. Current metrics are strong but spread across multiple scripts/reports. The next benchmark suite should produce one top-level summary that separates startup, movement, resident set, pop-in, queue, decode, terrain queue, GPU upload, collision, and render signals.

## Safe Acceleration Strategy

1. Measurement first: extend the benchmark suite before changing runtime behavior.
2. Keep rollback controls explicit: raw encoding, conservative batch, bootstrap radius, view distance, keep distance, and GPU feature flags must remain available.
3. Add pressure before policy: create start, long movement, spiral, fast turn, snap-back/teleport-like, high view distance, and high resident-set scenarios with shared pass/fail summaries.
4. Promote queue health to first-class evidence: record packet queue depth/max depth, per-frame drained count, stale latency, and starvation symptoms before adding backpressure.
5. Add pop-in metrics before changing scheduling: count missing visible/ground-adjacent chunks, late chunk frames, and player-facing holes.
6. Separate render-ready and collision-ready evidence: keep player spawn collision-gated, but measure how often collision refresh delays visible mesh queue progress.
7. Treat compression as data-dependent: rerun raw/RLE comparisons after any worldgen variety increase and before protocol changes.
8. Avoid GPU repack activation until resident-set pressure is real: require higher draw/subchunk/faces pressure, allocator failure or fragmentation evidence, and rollback smoke before advancing repack beyond preview.
