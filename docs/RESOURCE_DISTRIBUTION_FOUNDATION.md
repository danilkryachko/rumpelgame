# Resource Distribution Foundation

This document records the first deterministic resource-distribution layer for world generation. The current layer is metadata-only: it samples resource IDs from explicit world generator inputs and block coordinates, but it does not alter chunk bytes, block IDs, atlas assets, storage, protocol, renderer behavior, or default generation.

## Current Contract

- `resource_v1` is owned by `server/pkg/world/resource.go`.
- Inputs are `GeneratorConfig.Seed`, `GeneratorConfig.DimensionID`, world block `X/Y/Z`, and `ResourceAlgorithmVersionV1`.
- `WorldGenerator.SampleResource()` and `DeterministicResourceID()` return deterministic metadata for coal, copper, iron, or `none`.
- `ResourceDefinitionsV1()` exposes stable IDs, display names, Y ranges, and rarity values.
- The sampler rejects out-of-chunk Y coordinates as `none`.
- `TestResourceSamplerDoesNotChangeGeneratedChunkBytes` proves sampling leaves `flat_v1` chunk bytes unchanged.
- `scripts/resource_distribution_matrix_gate.sh` records the representative matrix hash `f2beb912cffae722b9ea0322c68caa58a853c3c953fa4a0a80e618b42924e430`.

## Rollout Boundary

The metadata layer exists so resource distribution can be tested before production ore block IDs, atlas tiles, material definitions, protocol compatibility, storage compatibility, RLE entropy, streaming, and visual-smoke evidence are added.

Resource metadata must not become chunk content until a separate generator version maps resources to approved block IDs and refreshes downstream evidence.

## Blocked Changes

- Adding ore block IDs without matching server/client registries, atlas capacity, material metadata, and compatibility tests.
- Changing `Chunk.Serialize()` or `ChunkData.blocks`.
- Changing default `flat_v1` generated bytes.
- Persisting resource metadata outside serialized chunk bytes without a storage design.
- Inferring hidden resources on the client from partial chunk data.

## Current Status

This layer is complete as a deterministic metadata foundation. Resource sampling is guarded and reproducible, while resource-to-block generation remains inactive until a versioned generator maps resource IDs to approved block IDs and supplies downstream serialization, storage, streaming, and visual evidence.
